## 9. CLI and observable behavior

Working name `harness` is provisional. Planned commands:

- `harness ask --workspace <path> --provider openrouter --model <model-slug> "task"`
- `harness auth login chatgpt`, `harness auth status`, and `harness auth logout chatgpt`.
- `harness models --provider chatgpt` and `harness ask --workspace <path> --provider chatgpt --model <account-model-slug> "task"`.
- `harness chat --workspace <path>` for successive prompts in a simple interactive session.
- `harness sessions list`, `harness resume <session-id>`, `harness sessions show <session-id>`, and `harness sessions delete <session-id>` (refuses unresolved work).
- `harness doctor` for redacted configuration/path/provider checks, with live connectivity checks explicitly selected.

Normal stdout is user-readable. `--json` emits versioned newline-delimited JSON events; diagnostics go to stderr. Define documented exit outcomes for success, failure, approval required, interruption, and cancellation. Persist terminal outcomes before publishing completion. Show whether usage/cost is measured, estimated, or unavailable. Monetary caps are advisory unless rates and provider enforcement support stronger claims; request/tool/time caps are locally enforced.

`--json` is output-only in v0.1. Interactive `ask`/`chat` handles approvals within the turn. After a non-TTY approval-required exit, `harness resume` in a TTY can approve, deny, cancel, or resolve uncertain work. Non-TTY resume returns the pending outcome again without executing it. A broken stdout pipe is observer loss and triggers cancellation/cleanup.

Escape terminal-control sequences in untrusted text and output; never render raw escape commands from files or model/tool content. Ctrl+C requests cancellation and then returns after bounded cleanup. Do not claim completion merely because a model says tests passed: report the actual verification command, exit status, and any skipped verification from stored tool results.
