## 7. Persistence and crash recovery

Keep application data outside repositories in a local OS data directory, with restrictive permissions. Do not place the live SQLite database on a network or cloud-synchronized filesystem. Multiple workspace processes can share the store; there is no single-writer-process assumption. Retain rollback DELETE journaling with `synchronous=EXTRA`, foreign keys, short transactions, and bounded busy handling. Read PRAGMA settings back to verify them. Use SQLite's backup interface for consistent backups; WAL is a later option. [SQLite synchronous modes](https://www.sqlite.org/pragma.html#pragma_synchronous)

Use `BEGIN IMMEDIATE` for short write transactions. Configure a 5-second busy timeout and a bounded persistence retry budget that never repeats an external effect. Lock contention is distinct from I/O/corruption failure. While recording a finished action, stop scheduling new work and retry its existing outcome; only exhausted persistence recovery becomes uncertain durable state. Readers do not hold transactions while streaming UI output.

Logical records: sessions/workspace identity, turns, complete messages, model attempts and usage, tool calls/attempts, approvals, durable events, output artifacts, and context checkpoints. Use transactions for related state changes, monotonic per-session event sequence numbers, foreign keys, and explicit migrations. Store lifecycle transitions and their events atomically. Keep the database authoritative rather than independently replaying two divergent logs.

Use a local OS-backed exclusive workspace lock whose lifetime follows the owning process, keyed by canonical workspace identity. Also enforce one unresolved running/suspended/interrupted turn per workspace and per session in storage. A second process gets a clear busy result. Acquiring the OS lock alone never authorizes automatic replay of a crashed action.

Turn states: `running`, `awaiting_approval`, `suspended_limit`, `suspended_recovery`, `interrupted`, then terminal `completed`, `failed`, `refused`, or `cancelled`. Persist suspension before intentionally releasing the OS lock. A new process holding that lock can atomically mark orphaned running work interrupted and inspect its pending batch; it cannot bypass it with a new session. Resume or explicit cancellation/abandonment resolves outstanding work while preserving prior results and consumed budgets. Cleanup uncertainty blocks new actions until reconciled.

Tool lifecycle: proposed, awaiting approval, authorized, intent recorded, running, then succeeded/failed/cancelled/unknown. Calls that never execute may end denied/stale/rejected/skipped; user-resolved uncertainty can end abandoned with an explicit unknown-effect result. Commit intent before work. Mark results complete only after artifact durability and database commit. Commit batch closure and its provider-facing result sequence atomically after every call is resolved. Denial/cancellation/unknown effects skip unstarted calls truthfully; an ordinary recoverable error need not skip later independent calls. No database transaction can atomically cover an arbitrary external command.

On restart:

- A completed recorded tool result is reused; the tool is not rerun.
- A pending approval is presented again with fresh validation and a new approval identity.
- An interrupted model stream is marked incomplete and may be retried; uncompleted tool fragments never execute.
- An incomplete read can be rerun against current state with a new attempt.
- An incomplete patch is reconciled with its before/after hashes and stored intent. If it already matches the expected final contents, record reconciliation; if unchanged, request approval again; if neither, stop for user resolution.
- An arbitrary command with unknown outcome is never automatically replayed. Show its command and captured output and require an explicit user decision to abandon or rerun. PID presence alone does not prove process identity or task success.

If persistence fails before execution, do not execute. If a command or patch may have succeeded but recording its result fails, halt the turn and surface uncertain outcome. Keep any recoverable artifact; do not claim rollback. Migrations back up the database consistently and fail without rewriting an unknown newer schema. Backup/export must redact credential values and state whether source code is included.
