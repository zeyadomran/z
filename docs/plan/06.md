## 6. Permissions, credentials, and process ownership

Policy modes for the first release:

- `inspect`: built-in scoped reads only; no patches or commands.
- `supervised`: scoped reads plus individual approval for every patch and command.

Approval binds to session, turn, call, normalized arguments, workspace, relevant file hash, and policy version. No approval reuse across changed arguments, changed file content, or restart. In noninteractive mode return `approval_required` and exit cleanly; do not hang awaiting stdin and do not auto-approve.

Patch approvals bind whole-file expectations. Command approvals bind executable/interpreter, full arguments/script, cwd, timeout, and environment overrides; they do not freeze every file a build might read. Show the full action, visibly escaping terminal, bidi, and invisible control characters. Never truncate a security-relevant preview into a misleading action.

Repository instructions guide the model but cannot change policy, credentials, execution mode, provider endpoint, or budgets. Tool output is untrusted task data. Preserve visible instruction provenance and cap instruction size/depth.

Obtain model credentials from an explicit host credential source; never put secrets in session records, command arguments, or logs. Start with an environment reference or OS credential store, with reference names persisted rather than values. Scrub provider secrets from child environments. Host commands still run as the user and can access user-readable files; hardened secret isolation requires a separately restricted execution environment.

On the supported Windows baseline, create a kill-on-close Job Object first and establish membership during process creation using `PROC_THREAD_ATTRIBUTE_JOB_LIST`, with explicit permitted handle inheritance. The job handle is non-inheritable. Fail closed if creation-time membership cannot be established. Do not use a create-then-assign sequence that leaves a crash window before assignment. Qualify launching from a host already in a parent job. The creation attribute requires Windows 10 or newer; qualify the actual supported Windows release rather than claiming support for every version. Use platform-specific support where plain Tokio spawning is insufficient. Job Objects provide process lifecycle grouping, not filesystem/network isolation. [Windows creation attributes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute), [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

M3 starts with a stable-Rust Windows launch spike using a small native `CreateProcessW`/STARTUPINFOEX implementation through supported Windows bindings. Qualify creation-time job membership, explicit handle inheritance, ordinary executable argument encoding, cancellable piped I/O, and parent-job behavior. Do not depend on nightly std extensions or suspend/assign/thread-enumeration, which leaves the SOL-01 crash gap. The spike must pass before live commands; failure does not authorize unowned spawning. [CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw)

Windows v0.1 uses no-window console launches and immediate `TerminateJobObject` for cancellation/timeout/output-limit shutdown. Report forced termination and possible partial effects. Do not promise graceful signaling without a shared console. Confirm shutdown through actual job/process state and bounded output draining, not notifications alone. Job Objects do not contain every indirect OS-mediated process creation; retain that host-mode limitation. A later Unix implementation may use graceful group signals before forced termination and reaping. Dropping a Tokio child alone is insufficient. [Windows console signals](https://learn.microsoft.com/en-us/windows/console/generateconsolectrlevent), [Tokio process behavior](https://docs.rs/tokio/latest/tokio/process/index.html)

Command lifetime includes managed descendants and output draining. After root exit, allow at most a fixed short drain/settle interval (initially 2 seconds), then terminate remaining owned descendants rather than waiting the full command deadline for a persistent build server. Preserve root exit code and report forced descendant cleanup/output incompleteness. Use `completed_with_cleanup` if descendants were killed; do not claim all child work succeeded because the root exited zero. Build servers are not persistent in v0.1. Never release workspace ownership with known active managed descendants; unconfirmed shutdown leaves an interrupted state that blocks new work until reconciled.
