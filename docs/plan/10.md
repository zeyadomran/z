## 10. Delivery sequence and acceptance gates

Each milestone is a small vertical slice. Start the relevant canonical behavioral test before implementing that slice. Early prototypes are internal and do not imply release readiness.

### M0 — Resolve contracts and scaffold

Create the two-crate workspace, pin the toolchain, define typed outcomes/events and initial schema, and record provider/platform defaults. Add configuration validation and a scripted provider. Define independent cancellation, shutdown ownership, and observer-loss semantics now. Gate: the CLI can invoke the core and print a deterministic completed turn without credentials. No tools execute yet.

Settle turn/batch/epoch states, crash takeover, provider outcome mappings, database concurrency, and a protocol-validating scripted provider before building dependent capabilities.

Resolve ChatGPT app eligibility/distribution requirements at this stage and implement the smallest secure sign-in/inference probe in M1b. Do not postpone proof of the required subscription route until packaging. Plan creation itself does not log in, access credentials, or make inference requests.

### M1a — OpenRouter read-only model loop

Implement the OpenRouter adapter, model/capability validation, explicit routing configuration, streamed output, scoped read/search/list tools, request limits, and protocol error handling, including durable tool-batch continuation. Persist accepted prompts and complete messages from the beginning. Establish workspace identity/locking and stale-state reconciliation before active tool turns, credential sourcing/redacted diagnostics before live requests, and terminal escaping before displaying untrusted content. Gate: a live manually invoked OpenRouter fixture explanation uses real file reads; a second process cannot execute in the same workspace; deterministic automated coverage requires no network or paid model. Protocol fixtures cover fragmented tool arguments, required reasoning-state round-trip, tool-result IDs, and midstream failure under HTTP 200; account failures and incompatible model options produce actionable outcomes.

Credential-file denial, scoped normalization for every read/search/list tool, hard context budgeting, and raw usage capture also land here. Caching options are capability-checked; effectiveness is observed rather than assumed.

### M1b — Required ChatGPT plan sign-in and read-only loop

Implement section 4.2, secure registration/token lifecycle, explicit provider/account selection, account model discovery, and Responses streaming/continuation. Reuse the same core scoped tools and policy. Gate: the intended account signs in through this application, completes direct subscription inference, invokes a harness-owned read tool, and continues with its result. Record actual eligibility and model availability. Deterministic protocol/auth fixtures cover malformed callbacks, mismatched state/nonce/account, expired or rotated tokens, unsupported fields, and usage-limit failure after streaming begins. An external access blocker must remain visible; it prevents a complete v0.1 release but need not stop independent M2–M5 development using OpenRouter and controlled provider fixtures.

### M2 — Supervised file edits

Implement patch previews, policy, approval binding, whole-file raw hashes, deterministic newline/BOM normalization, metadata-preserving staged writes, and patch intent/reconciliation. Gate: both LF and CRLF fixtures edit correctly, supported metadata is preserved, denial leaves content unchanged, and changed files invalidate previews. Inspect mode cannot mutate.

### M3 — Supervised command execution

Implement creation-time Windows process ownership, normalized command approval, child-environment credential scrubbing, concurrent bounded output capture independent of UI consumption, timeout/cancellation, and explicit uncertain outcomes. Gate: the agent runs the fixture verification command and reports the result; a spawned grandchild is stopped during cancellation, observer loss, launch-boundary parent termination, and normal launcher exit with lingering descendants under the documented policy. Validate executable paths with spaces and explicit batch-shim handling. No background processes or PTYs.

Start with the stable-Rust launcher spike and qualify cancellable pipe-draining primitives. Add durable output spooling, head/tail previews, and `read_tool_output` now, before a command can produce truncated output the model cannot retrieve.

### M4 — Resume and recovery

Finish fresh-process resume UX, unknown command handling, artifact consistency, and migration safeguards. Workspace locking already exists from M1. Gate: reopening a completed session preserves results without rerunning tools; an interrupted command cannot be silently replayed; resuming a partially finished tool batch produces a valid continuation without repeating completed effects. Disk failure does not lead to unrecorded new actions.

### M5 — Long sessions and usability

Add fresh-epoch compaction, session listing/show/delete, stable JSON events, usage presentation, and diagnostic usability. Output retrieval exists from M3; credential/terminal protections and raw usage capture exist before first use. Gate: a constrained-context fixture continues through a validated epoch without losing a requirement or replaying a completed effect.

### M6 — Qualify and package v0.1

Run required formatting, lint, build, and canonical functional coverage. Qualify Windows manually using owned fixtures, including spaces/Unicode, PowerShell, CRLF edits, interrupted process cleanup, fresh-process resume, and a clean user installation. Document host privileges and package a reproducible archive with checksums. Linux/macOS remain unsupported until later implementation and qualification milestones.

Release gate: both OpenRouter and direct ChatGPT plan access complete the canonical coding workflow through the same Rust engine, including tools, approvals, cancellation, and fresh-process resume. Verify provider/account identity and billing route remain explicit. Required subscription authentication, token refresh/reauthentication, and quota handling must be qualified. A key-funded OpenAI run or API-credit benefit cannot stand in for this subscription gate.

Implementation sequence: M0 → M1a → M1b → M2 → M3 → M4 → M5 → M6. If an external ChatGPT eligibility condition blocks M1b, independent work may continue, but M6 cannot pass until both providers are qualified. Persistence intent and approvals are prerequisites for mutation, even though complete recovery UX lands in M4. Required provider authentication is in scope; a hosted product account system, automatic updater, cloud backend, and desktop app are not prerequisites.
