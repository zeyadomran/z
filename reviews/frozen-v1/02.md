- An incomplete read can be rerun against current state with a new attempt.
- An incomplete patch is reconciled with its before/after hashes and stored intent. If it already matches the expected final contents, record reconciliation; if unchanged, request approval again; if neither, stop for user resolution.
- An arbitrary command with unknown outcome is never automatically replayed. Show its command and captured output and require an explicit user decision to abandon or rerun. PID presence alone does not prove process identity or task success.

If persistence fails before execution, do not execute. If a command or patch may have succeeded but recording its result fails, halt the turn and surface uncertain outcome. Keep any recoverable artifact; do not claim rollback. Migrations back up the database consistently and fail without rewriting an unknown newer schema. Backup/export must redact credential values and state whether source code is included.

## 8. Context and instructions

Instruction precedence: engine/system policy, current user's request, user-level preferences, project-root instructions, then applicable nested instructions. Project text cannot grant permissions. Load nested instructions before reading/editing files in their scope. Snapshot loaded instructions and their hashes so behavior can be explained later.

Use provider-specific token counting when available. Otherwise use a conservative estimate and reserve response/tool/schema headroom. Reject missing/invalid context-limit configuration; do not assume every model has the same limit. Use bounded ranges and output handles before summarizing conversation.

At the compaction threshold, only compact between complete model/tool cycles. Retain original user requirements when they fit, unresolved issues, decisions, modified paths, observed verification results, and recent complete exchanges. Preserve all original records. Persist the new summary/checkpoint before switching active context. A failed compaction leaves the prior context intact and returns a recoverable context-limit outcome if it cannot continue. Summaries cannot increase permissions. fx's separation of compacted context from original history is a useful reference. [fx compaction](https://fx.sh/docs/using-fx/context-compaction)

Provider-required opaque state must remain associated with its original message; if it cannot be preserved safely across compaction, begin a clean valid message sequence using the summary instead of fabricating protocol fields. Expose which history was compacted. Session storage is conversational memory; semantic/vector memory is deferred.

## 10. Delivery sequence and acceptance gates

Each milestone is a small vertical slice. Start the relevant canonical behavioral test before implementing that slice. Early prototypes are internal and do not imply release readiness.

### M0 — Resolve contracts and scaffold

Create the two-crate workspace, pin the toolchain, define typed outcomes/events and initial schema, and record provider/platform defaults. Add configuration validation and a scripted provider. Gate: the CLI can invoke the core and print a deterministic completed turn without credentials. No tools execute yet.

### M1 — Read-only model loop

Implement the first provider, streamed output, scoped read/search/list tools, request limits, and protocol error handling. Persist accepted prompts and complete messages from the beginning. Gate: a live manually invoked fixture explanation uses real file reads; deterministic automated coverage requires no network or paid model.

### M2 — Supervised file edits

Implement patch previews, policy decisions, exact approval binding, original-content hashes, staged writes, and patch intent/reconciliation. Gate: the fixture edit is correct, denial leaves the file unchanged, and a changed file invalidates the prior preview. Inspect mode cannot mutate.

### M3 — Supervised command execution

Implement Windows process ownership, command approval, concurrent bounded output capture, timeout/cancellation, and explicit uncertain outcomes. Gate: the agent runs the fixture verification command and reports the result; a spawned grandchild is also stopped during cancellation. No background processes or PTYs.

### M4 — Resume and recovery

Finish fresh-process resume, workspace locking, unknown command handling, artifact consistency, and migration safeguards. Gate: reopening a completed session preserves results without rerunning tools; an interrupted command cannot be silently replayed. Disk failure does not lead to unrecorded new actions.

### M5 — Long sessions and usability

Add bounded compaction, stored-output retrieval, session listing/show, stable JSON events, usage accounting, diagnostics, and credential/terminal-output protections. Gate: a constrained-context fixture continues through compaction without losing an unresolved user requirement or a completed tool result.

### M6 — Qualify and package v0.1

Run required formatting, lint, build, and canonical functional coverage. Qualify Windows manually using owned fixtures, including a workspace with spaces and Unicode, PowerShell invocation, CRLF edits, interrupted process cleanup, fresh-process resume, and installation into a clean user location. Document host execution privileges. Build a reproducible release archive with checksums. Linux may ship only after its own process/filesystem checks pass; otherwise label it unsupported for v0.1.

Dependencies: M0 → M1 → M2 → M3 → M4 → M5 → M6. Persistence intent and approvals are prerequisites for mutation, even though complete recovery UX lands in M4. No automatic updater, cloud backend, account system, or desktop app blocks this sequence.

## 11. Minimal functional validation

Follow the supplied minimal-functional-tests skill. Exercise the public engine interface using real internal modules, temporary workspaces, and a real temporary SQLite database. Substitute the external model endpoint and control external failures/time explicitly. Do not mirror every engine test through CLI, database, and UI suites.

Canonical success flow: prompt → scoped inspection → approved patch → approved verification command → observable final result → close/reopen history. Extend this owner as milestones land.

Separate material failure flows, added when the behavior is implemented:

1. Denied or stale approval cannot cause an edit or command; scope escape is rejected before action.
2. Truncated/malformed provider stream cannot execute partial tool calls; bounded retry preserves completed tool results.
3. Cancellation/timeout terminates the owned child tree and returns a truthful outcome with bounded output.
4. Crash recovery reconciles patches and refuses automatic replay of unknown command outcomes.
5. Failed persistence prevents new side effects and preserves a truthful uncertain result after an external effect.
6. Compaction failure preserves the previous history; successful compaction retains current requirements and complete call/result pairing.
7. A second process cannot start another active turn in the same workspace; schema mismatch cannot overwrite session data.

Group closely related branches in their canonical flow; create a new case only for independent behavior. Use deterministic subprocess fixtures for process behavior and separate real-platform manual qualification. Provider stream framing gets focused protocol fixtures because it is an external wire format. No GUI test matrix, stress infrastructure, arbitrary sleeps, or code-coverage percentage goal.

Revisit exact checks after the manifest exists.
