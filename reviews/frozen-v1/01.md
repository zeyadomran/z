# Rust coding-agent harness implementation plan

Status: draft v1, prepared for two independent reviews. This document specifies proposed work; no harness has been implemented or runtime behavior verified.

## 1. Outcome and scope

Build an original Rust agent engine and CLI inspired by fx. A user selects a local repository, submits a coding task, observes streamed progress, approves edits and commands, and receives a result supported by actual tool output. Sessions survive application restarts. The engine is reusable without terminal dependencies.

The first release is a supervised local developer tool for one user, with one active turn per workspace. Windows is the first supported platform; Linux support follows behind an explicit qualification gate. macOS is a later target. A working directory, process group, or Windows Job Object is not a security sandbox. Version one must describe command execution as running with the current user's host privileges.

Proposed defaults, subject to product preference rather than implementation ambiguity:

- CLI first; a desktop or web interface is deferred.
- Native Rust engine, not a wrapper around fx or another coding agent.
- One configured API-key provider first. Use Anthropic Messages as the initial concrete implementation target unless the user prefers another provider before implementation. Keep the selected model configurable; reviewer models are unrelated to this runtime default.
- File reads within the selected workspace run automatically after the user starts a session. Every edit and shell command requires approval. No automatic command-risk classifier in v1.
- Session data is local. Relevant code, instructions, and tool output are sent to the configured inference provider. No telemetry by default.
- No hosting requirement, subscription OAuth reuse, autonomous Git push/merge, browser automation, network MCP integrations, subagents, or persistent background commands in v1.

First demonstrable task: explain a small fixture repository, locate a simple bug, propose a patch, obtain approval, apply the patch, obtain approval for a verification command, run it, and report the observed outcome. Reopen that conversation in a fresh process.

## 2. Architecture and ownership

Use a Cargo workspace with two crates initially: `harness-core` and `harness-cli`. Keep core modules private unless the CLI needs their types. Avoid a separate crate per module and generic plugin frameworks.

The engine owns the active turn, policy enforcement, persistence, tool execution, and cancellation. The CLI owns input and presentation. The CLI cannot execute tools outside engine checks.

Core modules:

- `engine`: a single coordinator that owns turn state and serializes transitions. It assembles requests, consumes provider output, authorizes completed tool calls, and produces events.
- `provider`: request encoding and streaming response decoding. Preserve provider-required content blocks and opaque continuation data. A real provider and a deterministic scripted provider give this seam two actual implementations.
- `workspace`: scope resolution, instruction loading, bounded file search/read, and conflict-aware patches. Do not expose unrestricted filesystem handles to model-generated arguments.
- `execution`: supervised process lifecycle, concurrent stdout/stderr draining, output limits, timeout, and process-tree shutdown. Windows and Unix implementations satisfy the same observable contract.
- `policy`: deterministic decisions for a normalized action. Produces allow, deny, or request-approval; neither model output nor repository instructions can authorize an action.
- `store`: SQLite transactions, schema versions, durable events, tool attempt state, and compaction checkpoints. Use a concrete store, not an abstract database framework.
- `context`: request budgeting, complete-message selection, instruction hierarchy, output handles, and compaction preparation.

Initial public interface, described behaviorally rather than as finalized Rust signatures:

- Open an engine using workspace, provider, policy, limits, and a local data directory.
- Create or reopen a session; submit one user prompt and obtain a turn handle.
- The handle exposes events, approval responses bound to request IDs, cancellation, and a terminal outcome.
- List sessions and read their saved history. Session deletion is explicit and refuses an active session.

Domain types include `SessionId`, `TurnId`, `ToolCallId`, `AttemptId`, `ApprovalId`, `WorkspaceIdentity`, `ActionDigest`, and `EventSequence`. IDs are stable across restart. Persist schema version and provider identity. A session's provider cannot silently change on resume.

Events distinguish model text deltas, completed assistant messages, tool proposals, approvals requested/resolved, tool start/output/finish, usage, and terminal outcomes. Durable state is authoritative; UI delivery is not an execution acknowledgment. Text deltas may be ephemeral, but completed messages and tool transitions are durable. Use bounded channels; never drop approval or terminal events silently.

## 3. Rust implementation choices

- Tokio for asynchronous I/O, timers, channels, and coordination. Run blocking database work on a dedicated blocking worker; never hold a SQLite transaction across network or process awaits. [Tokio](https://tokio.rs/)
- reqwest with explicit timeout, TLS, redirect, and proxy configuration for model HTTP requests. Do not forward credentials across origins. [reqwest](https://docs.rs/reqwest/latest/reqwest/)
- Serde and serde_json for versioned persisted records and provider/tool messages. Reject malformed tool arguments and unsupported required fields. [Serde](https://serde.rs/)
- rusqlite with a bundled, patched SQLite release for reproducible local packaging. Record the actual selected version and its security review at implementation time. [rusqlite](https://docs.rs/rusqlite/latest/rusqlite/)
- clap for command parsing. Keep the first UI line-oriented; no full-screen TUI or PTY requirement. [clap](https://docs.rs/clap/latest/clap/)
- Structured local diagnostics with tracing; record IDs, statuses, durations, and usage rather than raw credentials or prompts by default. [Tokio tracing](https://tokio.rs/)

Pin a supported stable Rust toolchain and commit Cargo.lock for the executable. Choose dependency versions when implementing, after checking compatibility and licenses. Native OS calls for process ownership live in a small reviewed module. No broad agent framework is required.

## 4. Provider and agent loop

Start with a single request/response protocol and one configured model. The provider module exposes capabilities including tool calling, accepted content types, context limits, maximum output, and usage availability. Unsupported options must fail clearly; do not silently ignore them.

For the proposed Messages adapter, implement SSE parsing across arbitrary byte boundaries, indexed text/tool blocks, tool JSON assembly, final stop reason, usage updates, and error events. Preserve any required signed/opaque content when reconstructing history. Execute nothing from a partial stream. [Messages streaming](https://platform.claude.com/docs/en/build-with-claude/streaming)

Turn sequence:

1. Acquire the workspace execution lock and persist the accepted prompt before acknowledging it.
2. Snapshot effective instructions and limits, assemble bounded context, and record a model attempt.
3. Stream displayable output while assembling the full response. Commit a completed assistant message only after a valid terminal response.
4. Validate all proposed tools, assign stable call identities, and process them sequentially. v1 does not parallelize tools.
5. For each call, normalize scope and arguments, evaluate policy, and await a specifically bound approval when required.
6. Persist execution intent, execute, store the outcome, and append a matching tool result to conversation history.
7. Continue the model loop until a valid final response, required user input, cancellation, recoverable interruption, or a configured limit.

Tool errors are structured results the model can use to repair its approach. Configuration/authentication failures terminate the turn with a clear user action. Distinguish a normal final response from output exhaustion, refusal, transport failure, and invalid protocol. Never label an interrupted or truncated response as completed.

Limit model attempts, tool calls, cumulative output, and elapsed turn time. Proposed initial limits: 30 model requests, 60 tool calls, 20 minutes per turn, 120 seconds per command, and a 5-minute absolute command ceiling. Limits are host-configured, surfaced to users, and cannot be raised by the model. Count compaction and retries against limits.

Retry transient provider failures with bounded backoff and Retry-After support. Limit to two retries before a completed response; discard incomplete assembled tool proposals. A retry can incur extra provider charges. After an authoritative complete response is stored, resume from that response rather than requesting a replacement. Never apply HTTP retry behavior to tool execution.

## 5. Tools and workspace behavior

Initial model tools:

- `list_files`: workspace-relative entries, ignore generated/VCS directories by default, bounded results and explicit pagination.
- `search_text`: literal search first, bounded matches with paths and line numbers; regex can follow if needed.
- `read_file`: bounded line or byte ranges and a content hash. Reject binary/unsupported encoding with a useful error.
- `apply_patch`: create or edit one UTF-8 text file per call, with expected original hash, exact match semantics, and a preview. No multi-file atomicity claim, fuzzy match, deletion, rename, permission changes, or symlink editing in v1.
- `run_command`: an explicit executable plus argument vector and workspace-relative cwd; use a separate explicit shell-script form only when necessary. Show the exact interpreter/script to the user. Both forms require approval.
- `read_tool_output`: retrieve a bounded range from a stored result handle belonging to this session.

Resolve absolute paths and workspace identity at session creation. Reject traversal, device paths, unsupported network workspaces, and paths resolving outside scope. For new files validate the existing parent. Treat symlinks, junctions, reparse points, hard links, and case-insensitive paths deliberately: reject unsafe/ambiguous write targets, and verify read targets remain in scope. Preflight and recheck at execution; do not promise race-free isolation against hostile concurrent filesystem changes in host mode.

Ignore rules are convenience, not access control. Default-deny common credential files and the harness's own data directory to built-in reads and writes; a user-selected file exception is explicit. This cannot prevent an approved arbitrary host command from reading user-accessible data. Document that limitation rather than presenting filename filtering as a sandbox.

Patches preserve existing newline style and fail if the file changed since the preview. Use a staged replacement appropriate to each OS; verify the final content hash and retain the prior contents/diff for review. If a conflict occurs, reread and propose a fresh patch with fresh approval. Never reset the user's working tree automatically.

Commands run without a terminal and with stdin closed. Programs requiring interaction fail with a useful explanation. Capture stdout/stderr concurrently as bytes; use bounded display decoding and preserve truncation metadata. Proposed limits: 64 KiB model preview, 10 MiB saved output per command, 100 MiB artifacts per session, 1 MiB input text file, and 256 KiB assembled tool arguments. When a command reaches its output-storage cap, terminate it and mark output-limited; continue draining during shutdown to avoid pipe deadlock.

## 6. Permissions, credentials, and process ownership

Policy modes for the first release:

- `inspect`: built-in scoped reads only; no patches or commands.
- `supervised`: scoped reads plus individual approval for every patch and command.

Approval binds to session, turn, call, normalized arguments, workspace, relevant file hash, and policy version. No approval reuse across changed arguments, changed file content, or restart. In noninteractive mode return `approval_required` and exit cleanly; do not hang awaiting stdin and do not auto-approve.

Repository instructions guide the model but cannot change policy, credentials, execution mode, provider endpoint, or budgets. Tool output is untrusted task data. Preserve visible instruction provenance and cap instruction size/depth.

Obtain model credentials from an explicit host credential source; never put secrets in session records, command arguments, or logs. Start with an environment reference or OS credential store, with reference names persisted rather than values. Scrub provider secrets from child environments. Host commands still run as the user and can access user-readable files; hardened secret isolation requires a separately restricted execution environment.

On Windows, start a child suspended, assign it to a Job Object configured to terminate owned processes when closed, then resume. If assignment fails, terminate the suspended process and report failure; never proceed unowned. Prevent inherited job handles. Use platform-specific support where plain Tokio spawning is insufficient. Job Objects provide process lifecycle grouping, not filesystem/network isolation. [Windows Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

On Unix, supervise an owned process group and reap children; do not claim a process group prevents deliberate escape. Cancellation requests a bounded graceful stop, escalates to forced termination, waits for exit and output drains, and then writes a terminal tool outcome. Failure to confirm shutdown becomes an explicit interrupted state. Tokio dropping a child handle alone is insufficient lifecycle management. [Tokio process behavior](https://docs.rs/tokio/latest/tokio/process/index.html)

## 7. Persistence and crash recovery

Keep application data outside repositories in a local OS data directory, with restrictive permissions. Do not place the live SQLite database on a network or cloud-synchronized filesystem. For the single-writer MVP use SQLite rollback journaling with explicit durable synchronous settings; WAL is optional later for concurrent readers, and requires checkpoint/backup handling. [SQLite WAL constraints](https://www.sqlite.org/wal.html)

Logical records: sessions/workspace identity, turns, complete messages, model attempts and usage, tool calls/attempts, approvals, durable events, output artifacts, and context checkpoints. Use transactions for related state changes, monotonic per-session event sequence numbers, foreign keys, and explicit migrations. Store lifecycle transitions and their events atomically. Keep the database authoritative rather than independently replaying two divergent logs.

Use a local OS-backed exclusive workspace lock whose lifetime follows the owning process. Also enforce one active turn per session in storage. A second process gets a clear busy result. Lock acquisition does not authorize automatic resumption of a crashed action.

Tool lifecycle: proposed, awaiting approval, authorized, intent recorded, running, then succeeded/failed/cancelled/unknown. Commit intent before external work. Mark returned results complete only after artifact durability and database transaction success. No database transaction can atomically cover an arbitrary external command.

On restart:

- A completed recorded tool result is reused; the tool is not rerun.
- A pending approval is presented again with fresh validation and a new approval identity.
- An interrupted model stream is marked incomplete and may be retried; uncompleted tool fragments never execute.
