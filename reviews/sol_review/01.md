## Prioritized findings

### SOL-01 — P1 — Suspended creation followed by job assignment has a crash gap

**Sections:** 6, Windows process ownership; 7, crash recovery; 10, M3.

**Problem and failure scenario:** The prescribed sequence creates the child suspended and assigns it to a kill-on-close Job Object in a second operation. If the harness process dies between those operations, the child is not in that job. It can remain suspended after the harness exits. Terminating it when assignment returns an error does not cover an abrupt parent death before assignment. This violates the intended owned-process lifecycle even though the unowned child has not yet executed user code.

**Suggested correction:** Establish job membership as part of process creation on the supported Windows baseline. Microsoft documents `PROC_THREAD_ATTRIBUTE_JOB_LIST` as a process-creation attribute on Windows 10 and newer. Set the kill-on-close job up first, supply its handle through the creation attribute list, keep the job handle non-inheritable, and retain fail-closed launch behavior. Explicitly qualify creation under a parent job. If the selected baseline cannot support creation-time membership, require a justified alternative that closes the crash gap rather than presenting the two-call sequence as crash-safe. The availability of the attribute is documented; the residual-process conclusion is my analysis of the proposed two-operation sequence. [Microsoft: process creation attributes](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-updateprocthreadattribute)

**Acceptance correction:** Extend the existing process/crash failure flow with a controlled parent termination at the launch boundary and verify that no owned fixture child remains. Use explicit fixture synchronization rather than sleeps. This is a blocker for M3's lifecycle guarantee, not a request for security sandboxing.

### SOL-02 — P1 — The durable unit of a tool-response batch is unspecified

**Sections:** 4, turn steps 3–7; 6, noninteractive approval; 7, resume; 8, complete-cycle compaction; 11, failure flows 1, 2, 4 and 6.

**Problem and failure scenario:** Sequential tool execution does not imply that the provider emits only one call. The plan appends a matching result per call, but does not specify when those results form the provider-facing next message or how all remaining calls are closed when a limit, cancellation, invalid call, denied approval, or restart interrupts the batch. For example, a stored assistant message contains two calls; the first finishes, and the CLI exits for approval on the second. A subsequent user prompt or continuation with only the first result can leave an invalid Messages history. Retrying the assistant response would also risk duplicating the first side effect.

**Suggested correction:** Define a durable pending assistant batch. Preserve provider call IDs separately from local attempt IDs. Store each call's outcome incrementally, but encode the complete set of results together in the immediately following user message before issuing another model request. Denied or intentionally skipped calls receive truthful error results. An unknown command receives an uncertainty result only after the required user resolution; never invent success. An approval-required exit suspends the pending batch, and resume completes or explicitly abandons that batch before accepting an ordinary new conversation message. A completed result remains reusable throughout.

For a smaller MVP, explicitly configure `tool_choice: { type: "auto", disable_parallel_tool_use: true }` and validate the at-most-one-call contract. Cancellation and resume must still resolve that single pending call. Anthropic documents both the batch-result rule and this single-call option. [Anthropic: parallel tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use) Results must also directly follow their tool-use message. [Anthropic: handle tool calls](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)

**Acceptance correction:** Extend the canonical provider/recovery failure flow with a complete assistant response interrupted after one recorded result and before the next approval. Reopen through the public engine interface and verify a valid next request and no repeated side effect. If single-call-only is selected, test that narrower contract instead. This is a protocol contract blocker for M1 and its later mutation/resume extensions.

### SOL-03 — P1 — Bounded event delivery needs a cancellation and observer-loss contract

**Sections:** 2, coordinator, turn handle and bounded channels; 5, output draining; 6 and 9, bounded cancellation.

**Problem and failure scenario:** Bounded channels constrain memory, but the plan does not say what happens when the consumer stops reading or drops its turn handle. If the coordinator awaits a full output-event channel, it may stop servicing cancellation or deadlines. If a pipe reader awaits event delivery, the child can fill its pipe and block. The command can then outlive the promised bounded Ctrl+C cleanup. Persisting events first does not by itself prevent either wait.

**Suggested correction:** Require that pipe draining, process shutdown, and cancellation never depend on UI progress. Make cancellation available independently of the ordinary event queue. Coalesce or omit ephemeral display deltas under pressure while preserving bounded stored output and explicit truncation information. Keep durable approval and terminal states queryable by sequence even when delivery fails. For the MVP, define a disconnected consumer as cancellation with owned cleanup; supporting detached background turns is unnecessary. The contract should also state who owns cleanup when the handle or engine is dropped, and how an explicit asynchronous shutdown waits for that cleanup.

**Acceptance correction:** Extend the existing cancellation flow by deliberately pausing or disconnecting the event consumer while an owned fixture produces output, then request cancellation and verify shutdown and a truthful durable outcome. This is a material independent failure path, not a throughput benchmark. Settle this before M3 claims bounded execution cleanup.

### SOL-04 — P2 — Several mandatory prerequisites are scheduled after their first use

**Sections:** 6 and 9, credential and terminal handling; 7, workspace lock; 10, M1–M5.

**Problem and failure scenario:** M4 says it finishes workspace locking, and M5 adds credential/terminal-output protections. Yet M1 already displays live provider and repository content, M2 mutates files, and M3 launches host processes. Taken literally, the sequence permits two M2/M3 processes to operate in the same workspace, raw terminal control sequences to reach the CLI, or a provider credential to be inherited by M3 children before the relevant protections land. Calling prototypes internal limits exposure but does not resolve the milestone dependency ambiguity.

**Suggested correction:** Move the minimal workspace identity/lock contract ahead of the first active tool turn, terminal escaping to the first display of untrusted content, and credential sourcing/redacted diagnostics to the first live provider request. Require child-environment scrubbing in M3. M4 can still finish recovery UX and migrations; M5 can add compaction and usability. Clarify that new turns after restart reconcile stale durable active states while holding the workspace lock. Keep the existing linear milestone sequence; no extra infrastructure milestone is needed.

**Acceptance correction:** Attach the existing second-process exclusion flow to the first milestone that introduces locking. Put observable credential and terminal-output assertions at their owning provider/process/CLI boundaries rather than duplicating the full agent flow. This is an ordering correction before the affected milestone, not a blocker to M0.

### SOL-05 — P2 — Windows command normalization must include executable resolution and interpreter behavior

**Sections:** 5, `run_command`; 6, normalized approval binding; 10, M3 and M6.

**Problem and failure scenario:** An executable name plus an argument vector is not a universal literal-argument guarantee on Windows. Common developer entry points are `.cmd` shims, and interpreters have their own argument parsing. A user can approve a display that appears to be a direct executable invocation while the launch path adds command-interpreter parsing. Separately, resolving a bare executable name only after approval leaves the actual selected executable outside the reviewed normalized action.

**Suggested correction:** Specify which direct-launch executables v1 supports and resolve the actual executable/interpreter path before constructing the approval digest and preview. Recognize `.cmd`/`.bat` entry points as interpreter execution: either use the already planned explicit script form with a visible interpreter and full script, or reject them with actionable guidance. Do not advertise shell-free argument semantics for arbitrary interpreters. Preserve the resolved launch specification through execution and invalidate approval if normalization changes. This does not require hashing every installed tool or defending against a hostile user modifying their own machine.

Rust explicitly warns about nonstandard argument decoding by `cmd.exe` and batch files; Microsoft also documents that batch execution requires a command interpreter. [Rust: Command argument caveats](https://doc.rust-lang.org/std/process/struct.Command.html#method.arg), [Microsoft: CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw)

**Acceptance correction:** Extend the command approval/launch flow with an owned executable path containing spaces and a batch-shim case, including literal shell metacharacters in arguments. Assert the actual intended behavior, or the documented rejection, without executing a destructive fixture. Resolve before accepting M3's normalized approval contract.

### SOL-06 — P2 — Define normal command completion when descendants remain alive

**Sections:** 1, no persistent background commands; 5, capture and limits; 6, lifecycle; 10, M3.

**Problem and failure scenario:** The plan clearly specifies tree shutdown for cancellation, but normal success is not defined when the initial process exits before a descendant. A launcher can exit zero while a grandchild keeps the stdout pipe open or continues modifying the workspace. Waiting for EOF without a lifecycle-wide deadline can hang; reporting success and releasing ownership can leave an active background command despite v1's scope restriction.

**Suggested correction:** Define command lifetime to include all managed descendants and output drains. On initial-process exit with remaining descendants, use one explicit MVP policy: finish bounded draining and terminate the remaining owned job, or wait within the original command deadline and then terminate it. Report that descendant cleanup occurred rather than deriving overall success solely from the first PID's exit code. Never release the execution lock or report completed cleanup while the managed job is still known active. Keep an explicit interrupted/unknown outcome if shutdown cannot be confirmed. Job Objects manage associated processes as a unit, but do not make initial-process exit equivalent to job completion. [Microsoft: Job Objects](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)

**Acceptance correction:** Extend the owned process flow with a parent that exits normally while a synchronized grandchild remains alive and holds an output handle. Verify the chosen policy, bounded cleanup, and truthful result. This is separate from a cancellation-only grandchild assertion and must be settled in M3.

### SOL-07 — P2 — Staged patch replacement lacks an explicit metadata-preservation contract

**Sections:** 5, no permission changes and staged replacement; 7, patch reconciliation; 10, M2 and M6.

**Problem and failure scenario:** Checking final text hashes cannot establish the stated absence of permission changes. A generic temporary-file replacement can change a Windows file's ACL or other relevant metadata while producing exactly the expected bytes. Hash-only reconciliation would classify that edit as successful. The analogous executable-mode issue matters if Linux later qualifies.

**Suggested correction:** Add an explicit requirement to preserve supported security metadata for existing files and fail closed when that preservation cannot be performed. Choose the native replacement procedure accordingly; avoid Windows flags that ignore ACL merge errors. Keep recovery artifacts sufficient to explain partial replacement failures. Document unsupported metadata cases rather than implying that byte equality covers them. This is a file-integrity correction within the existing patch tool, not a request for broader filesystem features. Microsoft documents ACL preservation, optional flags that bypass it, and partial-failure states for `ReplaceFileW`. [Microsoft: ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew)

**Acceptance correction:** Extend patch qualification with an owned Windows fixture whose permissions differ from default inheritance, checking content and preserved access behavior. Linux mode preservation belongs to its later qualification gate. This can be settled during M2's native write design; it need not delay M0/M1.

## Assessment of the remaining design

**Architecture depth and Rust feasibility:** Two crates and concrete private modules are appropriate. A single coordinator owning state transitions is a useful boundary; the scripted provider supplies a real second implementation without speculative plugin abstractions. Dedicated blocking SQLite work and transactions kept out of network/process awaits are sound choices. The Windows launcher and filesystem replacement deserve the planned small native modules. They are the main platform-specific complexity, not reasons to replace the architecture.

**Provider protocol:** Arbitrary SSE fragmentation, indexed block assembly, preservation of signed/opaque content, complete-response gating, and distinct nonfinal stop outcomes are correctly identified. Retain these requirements. Provider-version headers and exact supported request options should be pinned in M0/M1's adapter contract. Handle ignorable unknown event types without accepting unknown executable tool content. Streaming usage updates are cumulative, so accounting must replace/merge the current snapshot rather than sum every update. These are implementation notes, not additional blockers. [Anthropic: streaming messages](https://platform.claude.com/docs/en/build-with-claude/streaming) Treating output/context exhaustion as truncation agrees with the documented stop-reason distinction. [Anthropic: stop reasons](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons)
