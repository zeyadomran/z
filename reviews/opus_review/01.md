## 1. Verdict

**Not ready to implement as written. Ready after a targeted revision; no re-architecture is needed.**

The architecture, scope, and honest security position are sound. The two-crate layout, engine-owned policy, durable tool intent, and refusal to replay unknown commands should all stay. The weaknesses sit where the plan's abstractions meet real contracts: the current Messages API rules, Windows process behavior on stable Rust, and SQLite under more than one process. Most fixes are a paragraph of contract text.

Following the plan literally would produce three kinds of failure:

- Sessions that the API rejects permanently (OPUS-01, 02, 03).
- A Windows command tool that cannot run `npm test` and can hang on successful builds (OPUS-05, 07).
- Safety controls that arrive after the features they protect (OPUS-08).

## 2. Blocking findings

### OPUS-01: Tool batches have no closure rule, so history can become permanently invalid

- **Severity:** Critical. **Blocker before M0.**
- **Sections:** §4 steps 4–7, §6, §7 restart rules, §8.
- **Problem:** One assistant message may hold several `tool_use` blocks, and each needs a `tool_result`. All results must return in one user message, with no text before them **[Doc]**. Step 6 appends results per call. The plan never says what happens to the other calls in a batch when one is denied, goes stale, is cancelled, hits a limit, or ends as unknown.
- **Failure scenario:** The model proposes a patch and a command in one response. The user denies the patch, presses Ctrl+C, or the process crashes. The durable history now ends in unanswered `tool_use` blocks, and every later request fails with a 400 **[Inference from the pairing rule]**. Because the bad tail is durable, resume cannot repair the session. Choosing "abandon" for an unknown command has the same effect.
- **Correction:**
  - Define a tool batch: one assistant message, closed by exactly one user message holding one result per call, in order.
  - Persist per-call outcomes as they happen, but append the closing message to history only when the batch closes, in one transaction.
  - Give every path that does not run a tool a synthesized `is_error: true` result. That covers denied, stale, policy-rejected, cancelled, limit reached, unknown, and abandoned.
  - After denial, cancellation, or an unknown outcome, give unstarted calls a `skipped` result. An ordinary tool failure does not skip the rest.
  - Keep parallel tool use enabled. The API explicitly allows sequential execution, so §4's sequential rule needs no API setting **[Doc]**.

### OPUS-02: Request prefix is not frozen, which conflicts with thinking-block binding

- **Severity:** Critical. **Blocker before M0.**
- **Sections:** §2, §4 step 2, §6 modes, §8.
- **Problem:** On Opus 5.5, thinking cannot be disabled **[Doc]**. A thinking block's signature binds the top-level `system`, the tool set, and all earlier messages. Changing any of them invalidates later blocks. Where enforced, the result is a 400 that fails identically on retry. Opus 5.5 enforces this for accounts created on or after 2026-08-31. Older accounts are recorded but not rejected **[Doc]**. I do not know this account's creation date, so the plan must assume enforcement.
- **Failure scenario:** Step 2 snapshots instructions per turn, and §8 loads nested instructions mid-turn. If either changes `system`, the next request fails on an enforced account. The same happens if a session reopens in `inspect` with a smaller tool list. On older accounts it fails silently instead: no error, but thinking continuity and the prompt cache are lost.
- **Correction:**
  - Freeze `system` and the full tool list at session creation. Declare all six tools in every mode, and let policy deny them. Tools must also serialize deterministically.
  - Treat provider history as append-only and never rewrite a stored turn.
  - Deliver later instruction changes and nested instructions as appended content. Prefer provenance-labelled text inside the relevant `tool_result`, because this also avoids giving repository text system authority.
  - Keep §8's per-turn instruction snapshot as an audit record rather than a request input.
  - In the M1 live check, send `thinking.block_binding.prefix_mismatch_behavior: "error"` with beta `thinking-binding-controls-2026-08-01`. Setting that field opts any account into enforcement, so older accounts catch violations too **[Doc]**.

### OPUS-08: Safety controls are scheduled after the features they protect

- **Severity:** High. **Blocker before M0 (edit §10).**
- **Sections:** §5, §6, §9 versus §10 M1–M5.
- **Problem:** M5 carries "credential/terminal-output protections" and stored-output retrieval. M4 finishes workspace locking. But file content reaches the provider at M1, approval prompts appear at M2, and commands run at M3.
- **Failure scenarios:**
  - An M1 dogfooding run on a real repository sends `.env` contents to the provider.
  - At M2, a patch containing terminal control sequences overwrites the approval prompt, spoofing the only control in `supervised` mode.
  - At M3, child processes inherit the API key.
  - At M3, a failure past the 64 KiB preview is truncated, and the model cannot read it until M5.
  - Two processes patch one workspace, because the §4 step 1 lock is not finished until M4.
- **Correction:**
  - Move credential denial, output escaping, and the OS workspace lock to M1.
  - Move child-environment scrubbing and `read_tool_output` to M3.
  - Make the preview keep both head and tail, since failures usually appear at the end.
  - Persist raw usage fields from M1, because they cannot be backfilled.
  - Leave compaction, stable JSON events, and session UX in M5.

### OPUS-09: Turns have no state machine or crash takeover rule

- **Severity:** High. **Blocker before M0 (schema).**
- **Sections:** §2, §4, §6, §7, §9.
- **Problem:** Tools have a lifecycle, but turns do not. The tool lifecycle also lacks denied, stale, skipped, and abandoned.
- **Failure scenarios:**
  - A crash leaves a turn active. §7's "one active turn per session" then blocks the session, because no rule releases it.
  - `harness ask` exits with `approval_required`, leaving a turn with no owner. Another session in the same workspace can then start and change files around an unresolved action.
  - The 20-minute turn limit expires while a user reads an approval prompt.
  - `--json` emits approval requests, but no input path exists to answer them.
- **Correction:**
  - Define turn states: `running`, `suspended` (awaiting approval or a recovery decision), `interrupted`, and the terminal outcomes.
  - Add a takeover rule: a process that holds the OS lock and finds a `running` turn owned by an earlier process marks it `interrupted` in one transaction. Lock ownership proves the prior owner is gone.
  - Let a suspended turn block new turns in its workspace until it is resumed or cancelled. This preserves §1's one-active-turn rule.
  - Make `harness resume` the only v1 way to answer approvals, offering approve, deny, or cancel. In non-TTY mode it returns `approval_required` again. State that `--json` is output-only in v1.
  - Exclude human wait time from the elapsed-turn limit.

### OPUS-10: SQLite "single-writer" assumption is false

- **Severity:** High. **Blocker before M1.**
- **Sections:** §1, §2, §7.
- **Problem:** §1 limits turns per workspace, not per machine, and §2 uses one data directory. So two workspaces mean two writer processes on one database, and `harness sessions list` adds readers. In rollback mode, readers' SHARED locks hold up the writer's commit **[Doc]**. Separately, `synchronous=FULL` is "maybe not durable" in rollback mode. Only EXTRA is listed as fully ACID there, while FULL is ACID in WAL mode **[Doc]**.
- **Failure scenario:** A command succeeds. Recording its result hits `SQLITE_BUSY` from contention. §7 treats persistence failure as uncertain and halts the turn, reporting a false unknown outcome on a successful action.
- **Correction:**
  - Recommended: use WAL with `synchronous=FULL`, an explicit `busy_timeout`, and `BEGIN IMMEDIATE` for write transactions. The plan already requires a local disk, so WAL's same-host limit costs nothing **[Doc]**. Still handle occasional `SQLITE_BUSY`, which WAL can return in obscure cases, and keep the WAL file with any copy of the database **[Doc]**. `BEGIN IMMEDIATE` avoids read-to-write upgrade failures **[Verify]**.
  - Acceptable alternative: keep rollback mode with `synchronous=EXTRA`, the same busy handling, and correct text.
  - Either way, treat lock contention as a bounded retry and not a persistence failure. Only a failed retry enters the uncertain path.

### OPUS-11: Stop reasons and provider errors have no complete mapping

- **Severity:** High. **Blocker before M1.**
- **Sections:** §3, §4, §7.
- **Problem:** §4 names four abnormal outcomes, but the API has more, and several require specific handling **[Doc]**. "Reject unsupported required fields" could also break replay, because docs require clients to tolerate new event types.
- **Failure scenarios:**
  - A truncated `tool_use` parses as a valid partial object and runs. A refusal can also cut off a tool call **[Doc]**.
  - `model_context_window_exceeded` is stored as complete.
  - A prefix-mismatch 400 is retried, and it fails the same way **[Doc]**.
- **Correction:** Add this table to §4, and make the mapping exhaustive.

| Provider result | Action |
|---|---|
| `end_turn` | Complete |
| `tool_use` | Proceed only if all blocks are complete and valid |
| `max_tokens` | Never run tools. Text-only output is `truncated`, and a trailing tool call may retry once with higher `max_tokens` |
| `model_context_window_exceeded` | Treat as truncated, then enter the compaction path |
| `refusal` | Discard partial output and run no tools. Report the `stop_details` category and record usage |
| `pause_turn`, unused `stop_sequence`, unknown value | `invalid_protocol`, no tools run |
| `error` SSE event such as `overloaded_error`, or a stream ending early | Retryable within the two-retry limit |
| 429, 5xx, 529 | Retryable, honoring Retry-After |
| 401, 403 | Terminal, user action required |
| Other 400 | Not retried. Prompt-too-long enters compaction, and a thinking-binding mismatch stops the turn as a harness bug |

Also ignore unknown SSE event types **[Doc]**, and handle `ping`. Store assistant content as raw JSON so unknown block types and signatures replay unchanged. Accept an empty tool-input stream as `{}` **[Verify]**, because some tools may have no required arguments. Exclude a refused prompt from the next request by default, or the session will tend to repeat the refusal **[Inference]**.

### OPUS-12: Exact patch matching conflicts with CRLF files and the hash contract

- **Severity:** High. **Blocker before M2.**
- **Sections:** §5 `read_file`, `apply_patch`, patch paragraph; M2; M6.
- **Problem:** §5 requires exact matching, forbids fuzzy matching, and says newline style is preserved, but it never defines how these combine. CRLF is tested only at M6. Also unspecified: whether the hash covers a read range or the whole file, whether it is computed on raw bytes, what a new file's expected hash is, how BOMs are handled, and what happens above the 1 MiB limit.
- **Failure scenario:** The model reads a CRLF file and emits an LF patch. Exact matching fails each time, so edits on ordinary Windows repositories spin through retries until limits end the turn. If `read_file` hashes only a range, a change elsewhere in the file also goes unnoticed.
- **Correction:**
  - The hash is always SHA-256 of the whole file's raw bytes, even for range reads.
  - A new file requires an explicit "must not exist" expectation.
  - `read_file` returns LF-normalized text plus newline and BOM metadata.
  - `apply_patch` matches against that normalized view, then writes using the file's newline style and BOM.
  - Mixed-newline files are rejected with a useful error in v1. This is deterministic normalization, not fuzzy matching.
  - Range reads remain available for files above the limit. Editing them is rejected.
  - Move the CRLF fixture into the M2 gate.

### OPUS-04: Suspended spawn on stable Rust has no chosen path

- **Severity:** High. **Blocker before M3.**
- **Sections:** §3, §6, M3.
- **Problem:** §3 pins stable Rust, and §6 needs suspend, assign, and resume. On stable, `CommandExt` offers `creation_flags` and `raw_arg`, but `ChildExt::main_thread_handle`, `spawn_with_attributes`, and `inherit_handles` are nightly-only **[Doc]**. The docs.rs `process_wrap::tokio` page shows no `JobObject` wrapper. The crate's Windows source does show a useful technique: resume via a Toolhelp32 thread snapshot **[Doc; page read through a summarizer, so Verify]**.
- **Failure scenario:** M3 discovers there is no thread handle available. The team then adopts nightly, contradicting §3, or writes raw `CreateProcessW`. That route loses std's argument escaping, including the batch-file protection added for CVE-2024-24576, and adds handle-inheritance and pipe work.
- **Correction:** Make a short spike the first M3 task. Recommended path: keep std/Tokio `Command` for argument handling, set `CREATE_SUSPENDED` with `creation_flags`, assign using the child's process handle, and resume through thread enumeration. If no thread resumes, terminate and report failure. Do not set either breakaway limit. Choose a different route only if the spike fails.

### OPUS-05: Normal command completion is undefined when a grandchild survives
